## 2. 何を作ったか（作業票 §2 の構成）

```
experiments/layout/
  lib/       spec(文字の段・色・書体)・content(芦屋堂の確定文言)・text(改行・実測)・browser(描画実測)・emit(絶対配置)
  a-box/     方式A：塊の入れ子 → CSS flex/grid/subgrid で書き出す
  b-anchor/  方式B：基準の木（resolve.mjs）＋ FEATURE/ITEMS の組み立て（model.mjs）
  ops/       編集の操作（E1〜E8）の定義（両方式が読む edits）
  scenarios/ 中身を変える試験（S1〜S7）のコンテンツ変形
  compare.mjs   両方式を同じ試験にかけ、数値と比較画像を出す
  expected-compare.json  付録A〜Cの書き起こし（値は変えていない）
```

- 対象は FEATURE（4.5）と ITEMS（4.6：甘味処の表・区切り線・ピルを含む全部）、PC1440・SP390。見出しの組（4.0）は両セクションの先頭要素として含めた。
- 文字・色・書体・大きさは芦屋堂の現データ（`samples/ashiyado`）と同じ値。カード／表の文言は本線 `resolveSite` で吐いた確定値を使用（`_dump_content.mjs`）。
- **本線の部品を再利用**：`tools/lib/measure.mjs`（高さ実測）、`tools/lib/linebreak.mjs`（BudouX・R2 の keep）、色・書体・フォント URL、`format`（価格・時間の文字化・ダンプ経由）。実測エンジンは本線と同じ PC=chromium／SP=webkit。**両方式は同じ実測値を使う**ので、文字の高さは一致する。
- 写真は幾何だけ要るので色板（asset id ラベル付き）で表現（参照元の写真・文言は不使用＝§11）。

## 10. 所見（判定ではない・作業票 §6.8）

作ってみて分かったことを、良し悪しの結論ではなく「難しさ」として書く。

1. **G1（同じ絵を出す）はどちらも問題なく到達した。** 差が出るのは「動かす・変える」ときだけ。静的な再現力は互角で、比較の本質は編集時のふるまいにある。
2. **方式B は座標を自分で計算するので、結果が決定的でエンジン差がほぼ無い（0.02px）。** 実測=計算なので G1 は構造上ほぼ自動で通る。反面、grid の折り返し・SP の行高・削除時の基準引き継ぎなど「ブラウザが普段やっていること」を全部自前で書く必要があり、**配置コードが厚くなり、書き忘れがそのままバグ**になった（S4・S6b で実際に踏んだ）。
3. **方式A は CSS に任せるので配置コードが薄く、折り返し・件数変化・行の縮みが“ただ動く”。** subgrid で価格の行そろえも素直に出せた。反面、**「ずらし」を相対オフセットで実装すると、後からのテンプレート変更（E8）と噛み合わない**。ここは編集画面に組み込むとき厄介：オーナーが動かした後にテンプレを直すと、見た目の間隔が意図とずれる。margin で実装すれば直るが隣を押す。
4. **編集画面（`editor_prototype.html`）への組み込みで困りそうな点**：
   - 方式A：オーナーの「ずらし」をどう持つか（相対オフセットか margin か）で、後からのテンプレ変更・自動整列との相性が変わる。E8 の非合成は、この選択の帰結。
   - 方式B：「落とした位置のすぐ上に基準を付け替える」は移動の追従（E1/E4）が気持ちよく決まる一方、**基準にしていた要素を消したとき（E5）の引き継ぎ規則**を丁寧に作らないと崩れる。中央そろえ・複数基準（列の下）まわりが特にデリケート。
5. どちらも「本線の実測（measure/linebreak）をそのまま使えた」のは大きい。文字の高さが両方式で一致するので、比較が幾何だけの勝負になった。
