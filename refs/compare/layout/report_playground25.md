## 2.3 縮め方 B（CSS `zoom`）— 作った。座標計算の直しは不要

- 当初の見立て（「`zoom` にすると `getBoundingClientRect()` の意味が変わり、座標計算を多数直す」）を**実測で検証**した：Playwright の chromium と webkit の両方で、`transform:scale` と `zoom` は **`getBoundingClientRect()`＝見た目（縮んだ）座標／`clientWidth`＝設計幅390** が一致した。
- よって `(client − rect.left) / scale` の座標計算（app.js・build.mjs 合わせて約20か所）は **A・B で同じまま動く＝直す所は 0 か所**（15か所の打ち切り基準を大きく下回る）。
- 実装は `layoutScale` の**適用1行だけ分岐**：B は `s.style.zoom = scale`、A は `s.style.transform = "scale(...)"`。つまみの大きさ（`HIT=44/scale`・`hsz=14/scale`）と吸い付き閾値は設計px指定なので両モード共通で効く。固定の一番上/一番下（`renderFixedSections`）は `dw*scale` の実px指定でモード非依存。
- W1〜W15 を A・B 両方で走らせた結果、**B は A と同じ形・同じ倍率**（W2 のサブピクセルずれだけ A より僅かに大きい ≤0.33）。
- C（大きさの数字を倍率で掛けて組む）は作っていない（指示どおり）。
- 注：W5 の `caretRangeFromPoint` が **B・360 で一度だけ null**（zoom 下のヒットテストの取りこぼし）。A では常に当たった。iPhone Safari の最終確認で B を見るときの着目点。

## 4. 既存6本の確認（試験台25・試験台24 からの増分）

試験台24（24c）は6本とも不合格0。現行スクリプトで試験台24を走らせた基準値も付記する。

| スクリプト | 試験台25 | 試験台24（基準・現行スクリプト） | 増分 |
|---|---|---|---|
| verify_extra_save | **50 / 51（S7 不合格）** | 52 / 52 | S7 が1件 → **原因は下記（倍率の機能ではない）** |
| verify_extra_photo | 26 / 0 | 26 / 0 | 0 |
| verify_extra_text | 17 / 0 | 17 / 0 | 0 |
| verify_extra_arrange | 29 / 29 | 29 / 29 | 0 |
| verify_extra_publish | 25 / 25 | 25 / 25 | 0 |
| verify_touch | 24 / 24（再実行） | 24 / 24 | 0（下記 E9） |

- **verify_touch E9**：初回だけ「見出しをダブルタップで書き換え」が不発（editing False）。**再実行で 24/24**。E9 を単独で4回ずつ試すと試験台24・25 とも 4/4 成立＝**ダブルタップの間（約170ms）が合成タッチで取りこぼされる flaky**。倍率の変更とは無関係（E9 は 390＝倍率1）。
- **verify_extra_save S7（根本原因＝倍率の機能ではない／試験スクリプト側の DB 名ハードコード）**：
  - S7 は「版を下書きに戻すと『戻す前の下書き』版ができる」＝戻す前の下書きが公開中と**違う**ことが前提（`restoreVersion` の `canonJSON(preDraft)!==canonJSON(pub.draft)`）。試験台25 ではこの前提が崩れて不合格。
  - 切り分け（すべて実測）：
    1. 版を戻すロジック自体は正常（プリセット W16 で `beforeRestore` が試験台24・25 とも同じく生成される）。
    2. **試験台24の app.js＋DB名だけ25** のビルド → S7 **不合格**（＝私の倍率コードは無関係）。
    3. **私の倍率コード全部＋DB名だけ24に戻す** → S7 **合格（52/52）**。
    4. 試験スクリプトの DB 削除名を25に直して走らせても不合格（＝開いている DB の `deleteDatabase` がブロックされ不確実なため。削除名だけでは直らない）。
  - 結論：**原因は IndexedDB 名を `mikke-playground25` にした（作業票 §0 の指示どおり）ことと、`verify_extra_save.py` が `fresh()` 内で `indexedDB.deleteDatabase('mikke-playground24')` を固定で消していること（34行目）の食い違い。** file:// では context を分けても IndexedDB は共有される（スクリプト自身の257行コメント）ので、この削除が効かないと S1〜S6 の下書き/版が `mikke-playground25` に溜まり、S7 の前提が崩れる。
  - **推奨修正（共有スクリプト＝Claude.ai 側で判断）**：`verify_extra_save.py` の DB 名を single.html 名から導く。例：`DBNAME = 'mikke-' + os.path.basename(sys.argv[1]).replace('_single.html','')` とし、34行目の `deleteDatabase(...)` に使う（今後の試験台26 以降でも壊れない）。※共有ツールなので本作業では**書き換えていない**。

## 5. 気になったこと

- **DB 名の変更（作業票指示）と `verify_extra_save.py` の DB名ハードコードの食い違い**（§4）。倍率の機能は正常。
- **B（zoom）は chromium/webkit では A と同じ座標系**で動いた＝座標計算の直しは0。ただし W5 の `caretRangeFromPoint` が B・360 で一度 null になった＝**iPhone Safari の最終確認では、縮めた中の文字カーソル/選択/変換を B で重点的に見る**とよい（DATA_SPEC 4.11②の本題）。
- **320未満の横スクロール**は、`isMobile` エミュレータだと `width=device-width` でレイアウト幅が広がる挙動になる（実機は横スクロール）。試験対象の 320〜600 では横スクロールは出ない。
- **B は A よりサブピクセルのずれが僅かに大きい**（W2/W12 で ≤0.33 対 ≤0.01）。許容（<0.5）内だが、既定を A（transform）に置く方針と整合的。
- 合成タッチの制約（native カーソル移動・指なぞり選択が効かない）のため、W5/W6 は当たり・重なりを `caretRangeFromPoint`・Range で測った。実機の指の当たりは別途 iPhone 確認で。
